# 面试技术亮点与诚实边界

## 建议的 3 分钟讲述

“我把一个 PDF/工单原型整理为单机企业试点知识库。管理员用原始 PDF 上传，文件原子保存、文档和任务事务创建；独立 Worker 领取任务、提取 PDF 文本并生成向量，审核发布后才可供工程师问答。问答 SQL 同时约束组织、设备型号、发布状态，模型答案还要通过引用编号校验。任务可靠性方面，我使用 SQLite 条件更新领取、租约 token 和过期恢复，防止两名 Worker 同时写回；数据库提交结果不确定时，核对持久化的完成尝试 token。”

## 可展开的工程细节

1. **权限边界**：`organization_id` 从服务端 API Key 配置得出，不接受客户端自报；详情、任务、发布、检索分别做隔离。旧匿名端点在试点配置下被屏蔽。
2. **文件与数据库**：先校验 PDF 头部/大小、计算 SHA-256；临时文件 `fsync` 后原子替换。文档和任务同一 SQLite 事务，失败时清理新文件。数据库和文件系统不是真正的分布式事务，异常崩溃仍需运维清理策略。
3. **并发 Worker**：`BEGIN IMMEDIATE` + 条件更新领取；`worker_id` 可复用，但每次领取的 `lease_token` 不复用。续租/成功/失败需持有活租约。
4. **不确定提交**：chunks、`review`、`succeeded`、`completed_lease_token` 原子提交。提交异常后先检查是否确为本 token 成功，再决定有限重试；不能把数据库异常当成 PDF 业务失败。
5. **可解释 RAG**：SQL 只取已发布且同企业/型号的片段，答案中的 `[资料N]` 必须匹配实际检索结果；没有有效引用返回待复核。
6. **测试证据**：临时 SQLite 上的并发领取、旧 token、防重复发布、回滚、历史恢复，以及原创真实 PDF 的 API → Worker → 发布 → 引用问答闭环。外部模型在离线测试中被模拟。

## 不应宣称

- 不存在可证实的生产客户、吞吐量、准确率或节省工时指标。
- `background` 不能保证崩溃恢复；Worker 需要外部进程监管。
- 离线模拟 Embedding/DeepSeek 不等于真实 API 联调。
- V1.0 未实现 OCR、恶意文件扫描、跨主机部署或成熟可观测性。
